# Проверка и защита лабораторной №2

## Соответствие критериям

| Критерий | Вес | Доказательство |
| --- | ---: | --- |
| Не менее шести микросервисов | 20% | Десять папок `services`, отдельные приложения и контейнеры, API, БД и конфигурация |
| Архитектура | 20% | `architecture.md`, границы ответственности, отсутствие SQL к чужим БД |
| Взаимодействие | 15% | REST Booking → Parking/Profile, Payment → Booking; события NATS |
| Persistence | 10% | Десять отдельных SQLite-томов, том JetStream, проверка перезапуска и перехода со старой базы |
| API и документация | 10% | OpenAPI/Swagger каждого сервиса, README и примеры API |
| Authentication/authorization | 5% | Подписанные JWT, роли, проверка владельца, закрытый ключ только Auth |
| Logging / errors | 10% | JSON-логи, общий Request ID, 401/403/404/409/422/503/504 |
| Тестирование | 10% | `tests`, `check.bat`, проверка реальных процессов и восстановления |

## Демонстрация за 10–15 минут

1. Запустите `start.bat`. Покажите `docker compose ps`: десять сервисов плюс Gateway и NATS. Объясните, какие контейнеры входят в число бизнес-сервисов.
2. Откройте Swagger двух разных сервисов. Покажите самостоятельные схемы и `/health`, `/ready` на прямых портах.
3. Зарегистрируйте пользователя, добавьте автомобиль, создайте бронь. Покажите отсутствие чужих броней и запрет изменения тарифа обычным пользователем.
4. Проведите учебную оплату. Покажите подтверждение брони и уведомление. Объясните, что подтверждение пришло событием, а не прямой записью в чужую БД.
5. Отмените бронь и дождитесь возврата в истории платежей.
6. Откройте `logs.bat`: найдите Request ID создания брони. Он присутствует у Gateway, Booking, Parking и Profile, затем переносится в событие.
7. Остановите Notification, создайте новую бронь, затем запустите Notification. Уведомление должно прийти после восстановления.
8. Остановите и запустите Booking. Покажите, что прежние брони сохранились.
9. Запустите `check.bat` и покажите итог тестов.
10. Покажите сценарий расширения: [обслуживание → лист ожидания → промокод → отчёт](expansion.md).

## Проверка сбоев командами

Откройте PowerShell в папке проекта.

**Отключение уведомлений как сервиса:**

```powershell
docker compose stop notification-service
```

Создайте бронь через UI. Основная операция сохранится, уведомление будет ждать потребителя.

```powershell
docker compose start notification-service
docker compose logs --tail 30 notification-service
```

Откройте раздел уведомлений. Проверьте, что уведомление одно.

**Недоступность синхронной зависимости:**

```powershell
docker compose stop parking-service
```

Попробуйте проверить места. Должна появиться контролируемая ошибка, серверный stack trace в UI не показывается.

```powershell
docker compose start parking-service
```

**Сохранность данных:**

```powershell
docker compose restart booking-service
```

Откройте историю броней после готовности сервиса. Данные должны остаться.

**Отказ брокера:**

```powershell
docker compose stop nats
```

Проверка готовности покажет деградацию. Уже запущенные сервисы продолжают принимать допустимые операции в свою БД и outbox. После восстановления события должны доставиться:

```powershell
docker compose start nats
```

## Вопросы на защите

**Почему это микросервисы?** Каждый сервис - самостоятельный процесс с API, логикой, данными и жизненным циклом. Связь выполняется по сети и через события.

**Зачем Profile отдельно от Auth?** Auth отвечает за идентификацию и подпись токенов, Profile - за пользовательские данные и автомобили. Изменение автомобиля не требует изменения учётной записи.

**Почему не общая БД?** Изменения хранилища одного сервиса не должны требовать SQL-изменений в остальных. Связь выполняется по ID и API.

**Почему SQLite допустима?** У каждого сервиса отдельная БД. Для одного экземпляра и локальной демонстрации этого достаточно. Масштабирование потребует изменения хранилища соответствующего сервиса.

**Как исключено двойное бронирование?** Проверка пересечений и вставка выполняются в одной транзакции записи Booking. Одновременные запросы сериализуются на уровне его БД.

**Почему уведомление может запоздать?** Это отдельный потребитель событий. Сначала фиксируется операция, затем доставляется и обрабатывается событие.

**Что если сообщение придёт дважды?** Inbox хранит обработанный ID. Повтор не создаёт повторный эффект.

**Что если оплата пришла после отмены?** Booking сохраняет отменённое состояние и публикует отказ подтверждения. Payment делает компенсацию возвратом.

**Чем отличаются health и ready?** Health проверяет HTTP-процесс, ready - возможность работы с собственной БД и брокером. Gateway дополнительно объединяет состояние всех сервисов.

**Почему контейнеров больше десяти?** Gateway и NATS обеспечивают маршрутизацию и доставку событий. Десять бизнес-сервисов считаются отдельно.
