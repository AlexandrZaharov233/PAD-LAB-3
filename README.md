# Лабораторная работа №3. Docker и Kubernetes

**ParkSlot** — система бронирования парковок из лабораторной №2. Здесь те же десять бизнес-сервисов, Gateway с веб-интерфейсом и брокер NATS JetStream. Комплект запускается локально двумя способами: Docker Compose или Kubernetes в Minikube.

щелчком. Файл можно сохранить отдельно от проекта: он скачает текущий проверяющий
код из этого репозитория. Python и Git устанавливать не требуется.

При первом запуске установится GitHub CLI, если его ещё нет, и откроется вход
в GitHub. Войдите как **AlexandrZaharov233**. Если появился одноразовый код,
введите его на странице, открытой GitHub CLI. Пароли и токены в исходники не записываются.

Сценарий самостоятельно открывает временное соединение с кластером, проверяет
API, оплату, балансировку Gateway и сохранность брони после замены Pod Booking.
Затем создаёт обычный commit с двумя файлами:
`test-results/local/latest.md` и `test-results/local/latest.json`.

Проверка создаёт учебную бронь, оставляет несколько Gateway и заменяет один

|---|---|---|

## 1. Проверка Docker Compose на Windows

Откройте Docker Desktop в режиме Linux containers. В новой папке дважды нажмите `start.bat`. При первом запуске скрипт создаст `.env`, соберёт образы и откроет [интерфейс Compose](http://127.0.0.1:8081). Адрес и пароль администратора записаны в `ADMIN_EMAIL` и `ADMIN_PASSWORD` этого файла.

Если `.env` уже создан, всю систему можно запустить командой:

```powershell
docker compose up -d --build --wait
docker compose ps
```

Ожидаются 12 контейнеров: десять бизнес-сервисов, Gateway и NATS. Откройте [статус Compose](http://127.0.0.1:8081/api/status). Для автоматического тестирования Compose запустите `check.bat`. Проверка создаёт примеры на учебной базе. Перед запуском Minikube можно остановить Compose двойным щелчком по `stop.bat`.

## 2. Установка Minikube и kubectl

Docker Desktop уже должен работать: `docker info --format '{{.OSType}}'` должен вывести `linux`. Обычный PowerShell:

```powershell
winget install -e --id Kubernetes.minikube
winget install -e --id Kubernetes.kubectl
```

Если `kubectl version --client` уже работает и совместим с версией кластера, повторная установка kubectl не нужна. Если winget недоступен, см. [установщик Minikube для Windows](https://minikube.sigs.k8s.io/docs/start/) и [варианты установки kubectl](https://kubernetes.io/docs/tasks/tools/install-kubectl-windows/). Закройте PowerShell и откройте новое окно. Проверьте:

```powershell
minikube version
kubectl version --client
docker info --format '{{.OSType}}'
```

Для первого запуска нужен интернет: Minikube загружает компоненты Kubernetes, Docker скачивает базовые образы и Python-зависимости. Для запуска приложения Python, NATS и БД отдельно устанавливать не надо.

## 3. Запуск в Minikube

1. В новой папке запустите `start-k8s.bat`. Он создаст профиль `parkslot-lab3` (4 CPU и 5120 МБ), соберёт и загрузит в кластер 11 образов приложения, создаст секреты, проверит манифесты через API Kubernetes и дождётся готовности. На первом запуске это может занять несколько минут.
2. Когда появится `Minikube is ready`, запустите `open-k8s.bat`. Дождитесь `Forwarding from 127.0.0.1:8082` и оставьте это окно открытым. Откройте [ParkSlot в Minikube](http://127.0.0.1:8082) и [статус системы](http://127.0.0.1:8082/api/status). В статусе должно быть 10 готовых сервисов.
3. Для входа администратором используйте `admin@parking.local` и значение `ADMIN_PASSWORD` из `.local/k8s.env`. Обычного пользователя зарегистрируйте в интерфейсе.
4. Для защиты запустите `verify-k8s.bat` из той же папки. Скрипт покажет ресурсы Kubernetes, выполнит реальную бронь и демонстрационную оплату, масштабирует Gateway и проверит сохранность брони после удаления Pod’а. Подробные команды и ожидаемые результаты есть в [сценарии защиты](docs/defense.md).

Если Docker сообщает о нехватке памяти Minikube, остановите лишние контейнеры. До первого успешного запуска можно выбрать меньше ресурсов:

```powershell
.\start-k8s.bat -Cpu 3 -MemoryMB 4096
```

Чтобы поставить лабораторную на паузу, закройте `open-k8s.bat` и запустите `stop-k8s.bat`. Он останавливает профиль без удаления томов. Чтобы продолжить работу, можно снова запустить `start-k8s.bat` или выполнить `minikube -p parkslot-lab3 start` для уже развёрнутого профиля и ещё раз открыть порт.

## 4. Что в проекте

| Файл или папка | Назначение |
|---|---|
| `services/*/Dockerfile` | 10 отдельных образов FastAPI. База `python:3.12.12-slim`, зависимости отдельным слоем, запуск под UID 10001 |
| `services/*/Dockerfile.dockerignore` | Каждый образ получает только зависимости, общие модули и исходники своего сервиса. Секреты и локальные данные исключены |
| `gateway/Dockerfile` | Образ Gateway и статических файлов веб-интерфейса |
| `docker-compose.yml` | Все контейнеры, локальные порты, проверка готовности, сохранение данных Compose |
| `k8s/deployments/` | 10 Deployment бизнес-сервисов, 1 Deployment Gateway и 1 StatefulSet NATS |
| `k8s/services/` | Стабильные DNS-имена HTTP-сервисов и брокера внутри кластера |
| `k8s/configmaps/` | Адреса сервисов, настройки приложения и файл конфигурации NATS |
| `k8s/secrets/` | Образец структуры Secret. Рабочие значения генерируются локально при запуске |
| `k8s/storage/claims.yaml` | 10 постоянных томов SQLite и отдельный том JetStream |
| `k8s/kustomization.yaml` | Подключает манифесты для одного `kubectl apply -k k8s` |
| `scripts/validate-lab3.py` | Проверка связей между YAML, Dockerfile и скриптом запуска без кластера |

В Kubernetes, например, Booking обращается к `http://parking-service:8000`, а сервисы подключаются к `nats://nats:4222`. `/health` показывает, что процесс отвечает; `/ready` учитывает готовность его зависимостей. Kubernetes перезапускает контейнер после повторных сбоев liveness и исключает неготовый Pod из маршрутизации Service по readiness. Дополнительная startup-проверка оставляет время на инициализацию.

| Контейнер | Requests CPU / RAM | Limits CPU / RAM |
|---|---:|---:|
| Восемь обычных сервисов | 50m / 96Mi | 500m / 256Mi |
| Auth и Booking | 70m / 128Mi | 700m / 384Mi |
| Gateway | 30m / 64Mi | 400m / 192Mi |
| NATS | 40m / 64Mi | 400m / 192Mi |
| Инициализация каждого постоянного тома | 5m / 8Mi | 100m / 32Mi |

Это стартовые бюджеты для локальной нагрузки, а не измеренные пиковые значения. Auth проверяет пароли с затратами памяти, Booking сводит несколько запросов и операций с транзакциями, поэтому им дан больший запас. `100m` CPU — 0,1 логического ядра. Kubernetes планирует Pod’ы по requests, CPU ограничивает по limits, превышение лимита памяти может привести к `OOMKilled`.

Для SQLite и JetStream используется хранилище Minikube. Короткий init-контейнер назначает права на подключённый том и завершается; само приложение и брокер работают без root. Каждый SQLite-сервис оставлен в одной реплике. Демонстрация масштабирует Gateway от 1 до 3: все копии работают с теми же backend-сервисами. Локальный ограничитель частоты входа действует отдельно в каждой копии Gateway; для общего лимита в промышленной среде нужен общий механизм.
